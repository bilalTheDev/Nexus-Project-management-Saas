1. Executive Summary
Nexus is a portfolio-grade, multi-tenant project management SaaS application inspired by modern tools such as 
Linear and Jira. It enables people to create workspaces, invite teammates, organize projects, manage tasks on a 
Kanban board, discuss work, and understand progress through dashboards and activity history.
The product is intended to demonstrate production-minded full-stack engineering: React UI development, 
Django REST APIs, relational data modeling, authentication and authorization, tenant isolation, testing, 
deployment, and a documented Git workflow.
Product principle: deliver a small, coherent, reliable product before adding advanced features. The 
MVP must work end-to-end in the deployed demo.

4. Core User Journeys
1. Visitor opens the landing page, reviews product features, and chooses Sign up or Log in.
2. User creates an account, verifies/activates it according to the chosen MVP email strategy, and signs in.
3. First-time user creates a workspace and becomes its owner.
4. Owner creates a project, selects a workflow/status set, and invites or adds teammates.
5. Member opens the project board, creates a task, assigns it, sets priority and due date, and moves it between 
statuses.
6. Teammates comment on the task; significant actions appear in the activity feed.
7. Workspace member views dashboard metrics, filters tasks, and opens task details.
8. User signs out; refresh/session behavior is handled safely and predictably.

6. Functional Requirements
6.1 Authentication & account
 Users can sign up, log in, log out, and request a password reset.
 Validate email uniqueness, password policy, required fields, and server-side errors.
 Use Django's built-in user model or a custom user model created at project start; do not change user model 
late in development.
 JWT access token should be short-lived; refresh token handling must follow the selected library's 
documented secure pattern.
 Prefer refresh token in an HttpOnly, Secure cookie in production, with appropriate SameSite and CSRF 
protections. If using Authorization headers for both tokens, document XSS risks and avoid persistent 
localStorage storage where possible.
 Authenticated API endpoints return 401 when credentials are absent/invalid; frontend handles expiry and 
re-login cleanly.
 Rate-limit sensitive authentication endpoints where feasible.
6.2 Workspaces & membership
 A user can belong to multiple workspaces.
 The creator becomes the workspace owner.
 Workspace slugs are unique; changing a slug must not silently break data relationships.
 Members have a role and membership status; only active members can access workspace data.
 Admins/owners can add existing users by email and change roles according to role policy.
 Prevent removing the final owner; define ownership transfer or block destructive action.
 All queries and mutations enforce workspace membership and tenant isolation.
6.3 Projects
 Create, read, update, archive and (with confirmation) delete projects.
 Each project belongs to exactly one workspace and has a unique human-readable key within that 
workspace.
 Project fields: name, key, description, status, optional start/due dates, creator, timestamps.
 Project list supports search, status filtering, pagination and sorting.
 Only authorized workspace members can access a project; role-specific mutations are enforced on backend.
6.4 Tasks & Kanban
 Create, view, update, archive/delete tasks according to permissions.
 Task fields: title, description, status, priority, assignee, reporter/creator, due date, position/order, project, 
timestamps.

 Tasks support statuses such as Backlog, To Do, In Progress, In Review, Done; status configuration can be

 Tasks support priorities: Low, Medium, High, Urgent.
 Drag-and-drop updates task status and ordering; server validates destination status and project access.

 Activity entries are created for important actions such as task creation, status changes, assignment changes,

 Activity records include actor, workspace, optional project/task target, event type, concise metadata, and 
timestamp.
 Activity feed is paginated and sorted newest first.
 Do not store secrets or unnecessary personal data in activity metadata.
6.6 Dashboard & notifications
 Dashboard shows active project count, tasks assigned to the current user, overdue tasks, tasks due soon, and 
completed tasks in a selected period.
 Metrics must be derived from authorized workspace data and have clearly defined date boundaries/time 
zone.
 Basic in-app notifications may be added for assignment and comment events; if scope is tight, ship the 
activity feed first.
 Notification read/unread state is per recipient and does not expose another user's private notification 
records.
6.7 Search, errors & accessibility
 Search and filters are reflected in URL query parameters where practical, allowing reload/share of views.
 Show loading, empty, success, and error states for all primary data flows.
 Use confirmation for destructive actions and optimistic UI only when rollback/error handling is 
implemented.
 Support keyboard focus, visible focus indicators, accessible labels, contrast, and keyboard operation for 
core workflows.
 Use consistent toast/inline error patterns; never show raw stack traces to users.

9. Database Recommendation & Deployment Fit
Recommended database: PostgreSQL
Use PostgreSQL because the product contains relational entities and needs consistent relationships among 
workspaces, memberships, projects, tasks, comments and activity. PostgreSQL supports foreign keys, 
transactions, unique constraints, indexing, and robust reporting queries.

Relationship rules
 A workspace has many memberships; a user can have many workspace memberships.
 A workspace has many projects; a project belongs to one workspace.
 A project has many tasks; each task belongs to one project.
 A task may be assigned to one user; an unassigned task is allowed.
 A task has many comments; each comment has one author.
 Activity events belong to a workspace and can reference a project/task when relevant.
 An assignee must be an active member of the same workspace as the task's project; validate this in backend 
service/serializer logic.
 Keep foreign-key deletion behavior deliberate. Prefer PROTECT or soft deletion for core business records 
and CASCADE only where data loss is expected.
Optional project-level membership is not required for MVP if all active workspace members can see all projects. 
Add ProjectMembership only if the product needs project-specific access controls; do not add complexity 
without a clear requirement.

API standards
 Return 200 for successful reads/updates, 201 for creation, 204 for successful deletion with no body, 400 for 
validation errors, 401 unauthenticated, 403 forbidden, 404 not found, and 429 when throttled.
 Paginated list response should have a consistent shape, e.g. count, next, previous, results.
 Use server-side validation for enum values, due dates, membership, status transitions and field lengths.
 Do not leak whether a private workspace/project exists to an unauthorized user; use a consistent 404/403 
policy.
 Document sample payloads, error responses, query parameters and authentication in API.md/OpenAPI.

14. Testing & Definition of Done
Required test coverage areas
 Authentication: valid/invalid credentials, duplicate email, expired token, logout/refresh behavior.
 Tenant isolation: user from Workspace A cannot list, read, edit or delete Workspace B records by changing 
IDs.
 Role permissions: member cannot perform owner-only member management; final owner cannot be 
removed.
 Projects: key uniqueness within workspace, invalid date ranges if constrained, unauthorized access.
 Tasks: valid status/priority, assignee membership, ordering updates, due-date filtering, task access.
 Comments/activity: only authorized users can comment; activity is emitted for relevant actions.
 Frontend: login validation, protected route, project creation, task card status changes, loading/error states.
 End-to-end: sign up/login  create workspace  create project  create task  move task  add comment  → → → → → →
dashboard shows expected counts.
Definition of Done for every feature
 Acceptance criteria are met and edge cases considered.
 Backend permissions and validation are implemented, not just frontend checks.
 Tests are added/updated and pass.
 Linting, formatting and type checks pass.
 Loading, empty, success and error states are handled.
 API documentation and README are updated when behavior or setup changes.
 Secrets and private data are not present in the diff.
 Feature is reviewed via pull request and merged only after checks pass.
